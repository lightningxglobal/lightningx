Aeron · PostgreSQL fencing · deterministic replay

撮合引擎故障恢复：leader 猝死到僵尸被 fence 的全时序

一句话贯穿：epoch（栅栏令牌）是唯一的安全边界——不是锁。leader 每次更替 epoch +1，并盖进输出流的高 16 位；任何来自更低 epoch 的消息都被消费端当作僵尸整条丢弃。锁只管"谁来发"，epoch 管"谁的话算数"。

PHASE 01
T+0 · leader 失联

fail-closed：先闭嘴，再退出

leader— · 无人续租
Leader-A
崩溃或 PG 不可达。LeaseGuard 本地 Instant TTL 到期 → is_lease_valid()=false，立即停止发布，不等 sqlx 超时。
失去 leadership 被引擎视为 fatal → 进程退出；重启后以 standby 身份从 journal 追赶。
leader_lease
A 停止续租，expires_at < NOW() 逐渐成立，租约进入"可被抢占"状态。
desk-server
order_update 断流；pending 的 REST/WS 请求开始等待。此刻 last_epoch 仍 = N。
PHASE 02
抢占 · one atomic UPSERT

谁先抢到租约，谁把 epoch +1

epochN → N+1 · leader-B
Standby-B
try_acquire 命中 WHERE expires_at < NOW() 的接管分支：epoch = leader_lease.epoch + 1 = N+1。
leader_lease
一条 INSERT … ON CONFLICT DO UPDATE 原子完成 holder=B、epoch=N+1。接管才 bump，续租不 bump。
用 PG 一行 UPSERT 而非 etcd/quorum：安全靠 epoch 令牌，不靠锁本身，且复用已托管资金的同一套基础设施。
PHASE 03
接管 · catch-up & publish

快照抬起点，确定性保证一致

epochN+1 · seq 从 1
B (now leader)
冷启动则 load_latest 恢复订单簿到 (snap_rec, snap_pos) → replay_from(snap_pos) 只补尾 → 切 live 输入。
因输入流确定性，B 重建的簿与死掉的 A 逐位相同——不是"接近"，是 bit-identical。
publish
开始 publish_order_update，盖 epoch=N+1，seq 从 1 起（新 epoch 段独立计数）。
desk-server
收到 epoch=N+1 > last_epoch=N → 记 failover 日志，last_epoch=N+1、seq 跟踪 reset=0，恢复正常消费。

the property it all rests on

为什么"高 epoch 永远压过低 epoch"是数学保证的

僵尸最大序号 epoch = Nseq = 2⁴⁸−1 stamp_epoch(N, SEQ_MASK)
新 leader 首帧 epoch = N+1seq = 0 stamp_epoch(N+1, 0)
因为 EPOCH_SHIFT = 48：(N+1)<<48 | 0  >  N<<48 | (2⁴⁸−1) —— 高位 epoch 一进位，就跨过整段低位 seq 空间。48 位 ≈ 每 epoch 281×10¹² 条消息，几十年用不完；epoch 到 65535 才回绕。
两条序列号别混淆。本图讲的是 OrderUpdate.sequence（epoch+seq，做客户端排序 + 防僵尸）。另一条 PersistFrame (publisher_id, seq) 是持久化去重用的，时钟播种、单调递增，由 pg/redis-writer 靠 checkpoint floor 做精确一次 / 至少一次——它与 epoch fence 正交：writer 重启靠 journal replay + floor 补齐，engine 重启靠 snapshot + replay_from 补齐。
